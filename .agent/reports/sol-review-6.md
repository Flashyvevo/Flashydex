## 2. Fix-round regressions and evidence traps

1. **Product regression: S6-01.** The new liveness policy kills a live shared worker on silence alone. The prior code could hang, but did not intentionally kill valid long SQL. False death can abort an install and interrupt unrelated USER work; unknown-outcome handling preserves recovery rather than proving loss.
2. **New retry is ineffective, not merely too short: S6-02.** The wrapper makes repeated calls but the pinned library returns its cached failed promise. The spec's page reload creates a fresh runtime, explaining why it can pass when the same-session production retry cannot. Raising only the attempt count/delay cannot repair this.
3. **Known test regression:** committed `e2e/pwa-image-cache.spec.ts:42–47` expects >60 writes/all concurrent images admitted. Slot admission intentionally skips busy images. Storage child reports `Expected >60, Received 35`. I did not execute it; this is attributed evidence. Update the spec to exercise skip-when-busy and separately test cap/LRU with controlled admission; do not remove the product bound or use an unbounded production slot count to make it green.
4. **Handoff is substantially safer but incomplete:** optional lock release remains only a test fake; driver-level quiet for 40 ms is not an application-job drain contract. The new gate must not be advertised as covering all SQLite mutations while WITH/SAVEPOINT/writable PRAGMA escape it. No existing core WITH-write/SAVEPOINT usage was found in my source search; this limits the demonstrated current exposure.
5. S6-03 and the residual tee problem predate the fix; they are newly demonstrated findings/residuals, not falsely attributed as newly introduced corruption. The approved core semantic change has no regression found in this review; its independent 375-test gate passes.

### Boot-retry bound/strategy assessment

No defensible fixed Chromium/Safari SAH-linger upper bound was established by this review, and I did not measure one. The browser/resource cleanup lifecycle must not be treated as a guaranteed “3 seconds.” The supplied kill result is **7/40** failures with the inner retry and no outer retry, not proof that handles linger for a particular duration. With failure caching, elapsed waiting alone is insufficient anyway.

After fixing actual reacquisition, a **policy** such as an elapsed 10–30-second bounded retry with capped backoff/jitter and a visible waiting/retry screen is reasonable to test; it is not a browser guarantee or a measured optimal budget. Keep the init watchdog longer than the whole retry/probe budget and suspend appropriately when hidden. On exhaustion preserve storage and offer user-driven retry; a live/frozen owner is handled by the Web Lock, never stale-timeout takeover. Record real per-attempt causes/times and test no-outer-retry crash loops plus Safari separately. Never retry SQL/COMMIT as part of pool boot recovery.

## ADR-055 assessment: accept-with-conditions

Accept the 64 KiB page-layout decision, not an unconditional cross-device performance claim.

- `tools/catalog-builder/src/build-db.ts:36,47–50,109–113,149–152` sets page size **65536 before first schema creation**, stays DELETE, VACUUMs, verifies the closed result. Builder tests/typecheck passed independently this round.
- SQLite header 16/17 sentinel **0,1** means 65536; bytes 18/19 are independent read/write-format bytes and must remain **1,1** for catalogs. New A importer validates both correctly. It still accepts historical 4 KiB geometry; no runtime fixed-65536 rejection found. Memory-pool 4/64 KiB import/header/hash tests passed; I did not repeat round 5's real-sahpool page-size export probe.
- Pinned importDb accepts a byte stream, not page-aligned chunks; B's <=256 KiB slices may cross pages. `cache_size` is set negative (`worker-core.ts:238`), so cacheKiB remains KiB, not pages. Validation currently defaults to 32768 KiB in client, while contract comment still says 1024: reconcile that documentation; total WASM allocation is not bounded by page-cache suggestion alone.
- Source SHA now matches catalog bytes actually imported because non-1/1 inputs reject **before** hashing/import acceptance. USER migration's separate normalization/source digest is explicit. No publisher-byte rewriting to satisfy a catalog hash.
- Native contemporary SQLite understands the file layout; shipped Capacitor/SQLCipher bridge open/integrity/refresh/rollback remains unexecuted here and native writes remain gated. Do not infer device proof from format compatibility.
- Future page deltas must bind exact base/target identity and page geometry; 4→64 KiB requires full-pack fallback unless the format explicitly rebuilds geometry. Refreshed active catalogs are not necessarily immutable original bases. Delta application is still deferred.
- Repaging changes bytes/length/hash: publish a new immutable version/manifests, never replace an existing version's bytes. No weakening of same-version/different-hash rejection.
- The new watchdog currently defeats the promise that slow older 4 KiB packs remain installable: fix S6-01 rather than rejecting valid historical packs or bypassing required integrity validation.

Performance provenance: supplied director evidence is 16.5 s onboarding install (download 0.4 / decode 7.9 / import 3.2 / validate 4.0), aggregate JS peak 35 MB, storage 121.7 MB, search/reload OK. Fix storage child separately reports full-install 15,407 ms. **Neither timing was rerun by me.** Those runs do not establish an upper bound for synchronous SQL on a mid-range phone or Safari.
