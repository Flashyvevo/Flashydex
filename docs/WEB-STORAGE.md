# FlashyDex production web storage — 2026-10-31

Status: architecture decision and builder contract, NOT an implementation or benchmark pass. The owner's 2026-10-31 web/PWA update supplied with this task is binding: Netlify HTTPS web/PWA is the primary distribution path; the owner is not yet an Apple developer. Capacitor stays for later, with iOS/TestFlight manual-only. This document supersedes the web-dev-only, jeep/sql.js, native-only full-catalog and HTTP-cache-only web passages in BRIEF's older text, ARCHITECTURE, CATALOG-PACKS and ADR-024/032/038/046/047. It does not change native storage or weaken COMPRESSION-STORAGE. ADR-049–054 and the appended web acceptance gates record the amendment.

## 1. Decision and source verification

Use `@sqlite.org/sqlite-wasm` inside one dedicated module Web Worker, explicitly installing the `opfs-sahpool` VFS. Start the builder spike with the exactly pinned `3.54.1-build1` package (npm registry latest returned this version, published 2026-10-19). Verify the resolved package/lockfile and shipped SQLite version before release; do not float `latest`. No package/code changes were made by this architecture task.

| Option | Decision | Reason |
|---|---|---|
| Official SQLite WASM + worker + `opfs-sahpool` | Selected | SQLite pages read/write OPFS files; no whole-database load/export for normal operation. No SharedArrayBuffer or COOP/COEP requirement. Compatible with the modern synchronous SAH API, including Safari iOS 17/18. Explicit single-owner coordination fits the existing Web Lock. [S1–S4] |
| Official `opfs` VFS | Not selected | Supports transparent cross-context concurrency, but uses SharedArrayBuffer and COOP/COEP, plus an async proxy subworker. Its pre-17 Safari subworker storage bug and cross-origin isolation complexity are unnecessary here. iOS 17/18 can support it; rejection is not a claim that they cannot. [S1] |
| jeep-sqlite/sql.js | Migration-only, rejected for production DB access | The complete SQLite file lives in WASM memory; export/save adds a full byte array. Owner's EN reference is 138 MB raw: raw image + one save copy alone is 276 MB decimal, before app, SQLite overhead, decode, IndexedDB cloning or JA; a third full image makes 414 MB. These are arithmetic lower-bound illustrations, not measured process peaks. Current web staging also allocates `Uint8Array(expectedBytes)`. A decoder worker alone cannot fix whole-DB sql.js opening. [S5, R1] |

Important version-specific safety: initialize with `clearOnInit:false`, `preserveOnInitFailure:true`, a stable directory and capacity. SQLite 3.54 introduced `preserveOnInitFailure`; the default false may remove the VFS storage on initialization failure. Never handle initialization failure by calling `removeVfs()`, `wipeFiles()`, clearing OPFS, or falling back silently to an empty memory DB. The downloaded pinned package source and types contain the preservation option, chunked import and pause APIs. [S1, S3]

The npm README's worker example uses `oo1.OpfsDb` (`opfs`), so its COOP/COEP warning is real for that example, NOT a universal requirement of all VFSes. Our worker explicitly calls `installOpfsSAHPoolVfs`, then uses the returned `OpfsSAHPoolDb`, not `OpfsDb`. Do not copy its transient in-memory fallback. Worker1/Promiser1 are deprecated in the fetched package README; use OO1 directly behind our own narrow message protocol. [S2]

All external sources below were fetched with `curl -L --fail`; source review is not Safari/device execution. SQLite trunk documentation is moving; the pinned npm bundle was additionally inspected for the critical APIs. A guessed OO1 source URL returned 404 and was corrected to `sqlite3-api-oo1.c-pp.js`. A guessed package `dist/sqlite3.mjs` returned 404; package metadata identified `dist/index.mjs`. The caniuse HTML endpoint returned 406; its raw feature JSON was retrieved instead. No missing result is represented as a successful test.

## 2. Browser support, capacity and lifetime

### Compatibility contract

Secure HTTPS top-level origin, workers, WASM, IndexedDB, Web Locks, `navigator.storage.getDirectory()` and usable synchronous `createSyncAccessHandle()` are required. Probe create/write/read/flush/close/reopen of a tiny ordinary OPFS file IN A WORKER before installing the VFS, then probe SQLite commit/reopen. Feature presence alone does not establish writable storage. Do not use the optional SAH `mode` argument: MDN BCD lists it as unsupported in Safari and Firefox. [S4]

| Browser | API evidence | FlashyDex support decision |
|---|---|---|
| Safari iOS/iPadOS 17.x and 18.x, Safari tab and installed Home Screen app | MDN lists OPFS/getDirectory and createSyncAccessHandle from Safari 15.2; fully synchronous close/flush from 16.4. SQLite recommends SAH pool for Safari 16.4+. | Production targets, subject to physical-device gates for both major versions and both launch modes. No COOP/COEP. Safari 17+ Storage API policies below apply. |
| Safari macOS 17/18+ | Same modern SAH interface | Supported after worker probe; desktop test does not close iPhone gates. |
| Chrome Android 109+ | BCD explicitly lists Android 109 for getDirectory, SAH and synchronous handle operations; do not substitute desktop Chrome 102 for the Android floor. | Supported feature floor; current stable Android Chrome is the primary measured Android target. |
| Chrome/Edge desktop 108+ | getDirectory Chrome 86, SAH 102, synchronous close/flush 108 | Supported feature floor, Playwright Chromium CI target. |
| Firefox desktop/Android 111+ | getDirectory and SAH from Firefox 111; Android mirrors Firefox in BCD | Supported storage design after runtime probe; release smoke required, Firefox persist() may display permission UI. |
| Older/unsupported engines, insecure origins, failed probes | Presence/UA is not enough | Storage-unavailable recovery screen, export existing legacy user data if possible, supported-browser instructions. Never allow a full-catalog sql.js fallback. |
| Private/Incognito | APIs may fail or provide temporary storage; quotas differ; data is normally deleted when private browsing ends. SQLite warns private modes may hide/restrict persistence. | Not a supported durable collection environment. Do not claim all private browsers lack OPFS. No reliable standardized private-mode detector; warn that private sessions are temporary, handle failures, and never label a probe/persist() result as proof of non-private browsing. |

Caniuse's broad File System Access feature includes user-visible file pickers and has partial-support notes. That is NOT the OPFS worker compatibility test; use the MDN per-method data and SQLite VFS requirements above. OPFS requires no visible file/folder picker or permission dialog. [S1, S4, S6]

### SAH capacity and connection ownership

Install one pool with stable directory `/flashydex-sqlite-v1`, VFS name `opfs-sahpool`, `initialCapacity:16`, `clearOnInit:false`, `preserveOnInitFailure:true`. Await `reserveMinimumCapacity(16)` on an existing pool (initialCapacity only applies to an initially empty pool). Capacity counts openable FILE SLOTS, not MB, DB rows, or number of simultaneous SQL queries. Default 6 is insufficient for our growth/recovery envelope. Keep the directory stable across app updates and never put ordinary staging files inside it. [S1, S3]

One writable USER plus EN and JA needs up to six main/journal slots, a candidate and its journal bring the planning subtotal to eight; previous generations, restore/migration candidates and SQLite temporary files need headroom. Sixteen is a starting allocation, not proof that arbitrary TEMP use fits. SQLite advises at least twice DB count and sometimes more than three times plus one. Measure `getCapacity/getFileCount/getFileNames` and available slots before imports/migrations. Grow with awaited `reserveMinimumCapacity` before the synchronous SQL operation when needed; the C VFS cannot auto-grow. Avoid large sorts/temp tables; keep queries bounded. Failure to reserve is a recoverable storage error, never delete USER to make room. [S1]

"Single connection" is an application safety policy, not literally one DB for the entire app: one worker/VFS owner, one physical connection per DB file, with independent USER and 0..n catalog connections. Current SQLite permits multiple handles in the same thread; versions before 3.54 had a same-thread locking corruption bug. We do not depend on multiple handles even with the new fix. CatalogSource read and writable logical wrappers share/refcount the same physical connection and queue; releasing a read wrapper must not close an in-use writer. Candidate validation uses a distinct candidate file; active validation borrows its existing physical handle. Portable TS joins remain; do not introduce ATTACH. [S1, R2]

Acquire the existing exclusive `flashydex-user-writer` Web Lock BEFORE worker/VFS initialization or legacy migration. Denied second tab opens NO SQLite/OPFS handles, even read-only ones; show the existing blocked-instance/takeover screen. A read-only tab would still contend for SAHs. Web Lock absence now fails closed for database opening, not merely writing. Hold it for the page lifetime, without `steal`; on explicit handoff drain, close every DB and terminate the worker before releasing it. Frozen owner tabs may delay takeover; do not force a new owner with a stale timeout. BroadcastChannel may advertise owner/version/status but is not a lock or SQL authority. Crash/unload releases the browser lock; takeover reloads and recovers before reading. This preserves the two-tab rule instead of promising concurrent writable tabs. [R3]

`pauseVfs()` (since SQLite 3.50) unregisters the VFS/releases SAHs and requires EVERY database/file on that VFS to be closed; it throws otherwise. `unpauseVfs()` asynchronously reacquires handles. They are useful for a future coordinated handoff, not per-catalog pause, rename, import activation, or concurrent tab access. Phase 1 does not need them for install. [S1, S3]

### Quota, Safari ITP and protection UX

For Safari 17+, including iOS 17/18: browser-app origin quota is UP TO 60% of total disk, overall browser quota UP TO 80%; other embedded WebKit apps have up to 15% per origin/20% overall. An installed standalone Home Screen web app receives browser-app quotas, not the 15% WKWebView tier. Cross-origin frames have a partition quota roughly one tenth of the embedding origin. These are upper bounds, NOT free disk guarantees or a reserved allocation. Do not advertise a universal 1 GB/500 MB iOS limit. OPFS, IndexedDB, Cache Storage and shell compete in the origin quota. Use `estimate()` and catch quota/short-write/I/O errors even when estimates look sufficient. [S7, S8]

Critical distinction: Safari ITP can delete script-written site data after SEVEN DAYS OF SAFARI USE without user interaction on that site when cross-site tracking prevention is enabled, not seven elapsed calendar days since a background fetch. This includes IndexedDB and SW registration/cache; OPFS is subject to browser-managed storage lifetime too. Synthetic clicks, heartbeats and scheduled downloads are not a mitigation. WebKit says Home Screen apps have their own use counter, actual app use resets it, and deletion of a first-party Home Screen app's data is not intended. That is the cited ITP mitigation; installation does not make data indestructible. [S4, S8, S9]

Use both protection measures, with exact claims:

1. Show a short "Protect your collection" sheet after the first successful personal save (and before first full catalog download), not a launch-blocking permission wall. Explain device-local data and export backup; a user tap runs `navigator.storage.persisted()` then `navigator.storage.persist()` if needed. Recheck on Settings/Data and standalone launch. Display actual `granted | best-effort/denied | unavailable | check failed`, last checked time, quota/usage and last export reminder. Do not say "prompt accepted" from a button click: Chrome and Safari normally use silent heuristics, Firefox may prompt. Home Screen installation is one WebKit grant heuristic, not a guaranteed grant. [S7, S8, S10]
2. Offer install guidance on iOS: Share → Add to Home Screen → open FlashyDex from its icon; dismissible contextual banner, hidden in standalone mode. On Android offer an install button only when `beforeinstallprompt` is available; otherwise browser-menu instructions. Never fake a universal browser install prompt. Explain the ITP risk for Safari-tab-only use and that periodic genuine use plus installing helps.
3. A granted persistent origin is protected from normal storage-pressure/best-effort eviction. The cited documents discuss ITP proactive eviction separately; do NOT promise that `persist()` alone overrides every ITP path or substitutes for the Home Screen mitigation. Quota errors, user clearing data, private-session closure, uninstall/container changes and device loss remain possible. Export JSON/.fdx outside the origin regularly; no local-only safeguard is a backup. Do not instruct users to disable privacy protections. [S7–S10]

Keep one canonical Netlify/custom HTTPS origin: origin includes scheme/host/port; deploy previews, localhost, custom domain and `*.netlify.app` are separate stores. Redirect alternate hosts to the canonical host before onboarding. Do not assume Safari-tab and installed-PWA storage containers/identities are shared across every iOS version; verify them, offer export/import guidance before switching, and never copy/merge collections automatically by name. A domain migration needs a user-driven backup/import bridge, not a new empty collection presented as data loss.

## 3. Core-unchanged driver and worker protocol

`packages/core` and its SqlDriver/ProxyCallback signatures, repositories, migrations, installer journal and transfer schemas stay UNCHANGED. Platform selection happens before creating services in `apps/mobile/src/platform/app-database.ts`: native uses the current Capacitor path; web uses `WebSqliteWorkerDriver`. The native sqlite-proxy object-alias workaround stays native; OO1 gives positional arrays directly. Existing catalog-source and install-port interfaces are the seam. [R2]

Implement `label`, `proxy(sql, params, method)`, optional `afterCommit`, `reopen`, `close`. Prepare/bind/step/finalize each statement in a finally block; use `Stmt.get([])` (or OO1 `rowMode:'array'`) in column index order. Preserve duplicate column names, aliases, null, empty string, zero and byte arrays. No `Object.values`, giant DTO hydration, JSON dump, catalog deserialize, whole-DB export or main-thread SQLite instance. Restrict input to bundled SQL/typed params, reject trailing second statements through SQLite preparation/tail facilities rather than splitting semicolons. Metadata/catalog SQL is never executable migration input. [S11]

| Proxy call | Return contract |
|---|---|
| all / values, SELECT, read PRAGMA, DML RETURNING | `{rows: unknown[][]}` in projection order |
| get | `{rows: firstPositionalRow ?? []}`; no nested one-row array, empty matches the CURRENT repo adapters |
| run without a row-producing result | `{rows: []}` after the statement completes |
| DML RETURNING, including compatibility run requests | Step all result rows; return rows in the same shape as the existing plugin's `changes.values` normalization. `db.changes()` is a count, NOT returned values. No new core reliance on RETURNING. |

OO1 stepping works for SELECT, PRAGMA and RETURNING without routing by a naive SQL-verb/RETURNING regex. Drain write/RETURNING statements to DONE even for `get`; returning the first row must not abandon completion. For `get` retain the first row while discarding subsequent rows, and for `run` discard non-RETURNING read output per the existing contract. Builders must test any RETURNING compatibility route separately; normal core remains UUID+SELECT. [S11, R2]

### Messages (version 1, all implementation confined to platform)

Every envelope has `{protocol:1, sessionId, requestId, op, dbId?, expectedGeneration?, payload}`. Session ID changes on worker restart; IDs are monotonically allocated per session. Responses echo IDs and contain either `{ok:true, payload, timings}` or sanitized `{ok:false, error:{code,message,sqliteCode?,retryable,commitState}}`. No SQL text/bind values/personal rows in diagnostic errors. `commitState` is `not_started | rolled_back | committed | unknown`, not a license to replay writes. Reject stale sessions/generations before execution; exactly one terminal response per admitted request.

Operations: `init`, `open`, `exec`, `batch`, `durableBarrier`, `reopen`, `close`, `cancel`, `stageImport`, `storageStats`, `shutdown`. Only adapter-private dbIds/refs are allowed, never arbitrary paths. Metadata control ops for activation use the same owner worker and serialized storage controller. Protocol mismatch fails safely and asks for update; no automatic wipe.

- `exec` payload is one `{sql,params,method}`. Main facade exposes precisely the existing Promise callback, not a new repository API.
- `batch` contains a bounded array of those statements; default <=25 statements/256 KiB serialized inputs and <=50 hydrated card rows per normal query. Results preserve statement order. It is NOT implicitly atomic. Internal adapter-only `atomic:true` wraps BEGIN/COMMIT/ROLLBACK only when no transaction is already active. Do not batch arbitrary awaited calls from different core tasks to improve latency.
- Core `Db.transaction()` already sends BEGIN IMMEDIATE, statements, COMMIT and then awaits `afterCommit`. Track transaction ownership per physical dbId; do not inject a second BEGIN, auto-commit an inner statement or let another wrapper's read slip into it. Share one admission/queue coordinator per physical connection across logical read/write/validation wrappers. If a transaction is open, unrelated wrapper requests wait until its owner ends it; preserve ordering without changing ProxyCallback or requiring core transaction tokens.
- Worker SQL runs synchronously but returns over async messages. Yield to the worker event loop between bounded operations; retain per-DB transaction ownership across yields, allowing other DBs' work but not other owners on the transactional connection. Use no await network/download inside SQLite transactions.
- `afterCommit` becomes an ordered durable acknowledgement/health barrier, NOT `saveToStore`. Use `journal_mode=DELETE`, `synchronous=FULL`, `foreign_keys=ON`, `mmap_size=0`, bounded cache settings, read back supported PRAGMAs. SQLite's OPFS xSync calls SAH.flush(); return success only after COMMIT/VFS writes complete. Error at COMMIT/barrier or worker death produces typed storage/persistence error, latches writes, reopens and reads receipts before retry. A timeout is not proof that a write failed. Never serialize/export a DB at commit. [S3, R2]
- Cancellation: remove a queued read without executing it, or mark an already-running read obsolete and discard its response. A cancel message cannot interrupt synchronous WASM currently blocking its worker; do not claim `sqlite3_interrupt` called by a later message interrupts that statement. Query limits and SQL progress/time budgeting are the first defense. Do not terminate the shared worker to cancel search. Mutations already committed remain committed; cancellation during a transaction is acknowledged only after rollback or commit determination. Pack cancellation uses a separate decoder worker/AbortController and stops before activation critical section.
- Worker failure rejects pending promises with unknown commit state, gates further writes and offers recovery/reload. `reopen` discards handles without jeep autosave, reopens the persistent file, revalidates FKs/journals, then core recovery resolves receipts. Never blindly replay bulkAdd/import. `close` finalizes statements/releases the logical ref, closes the physical connection only at refcount zero; application shutdown drains all before worker termination.

## 4. Files, streamed pack installation and atomic activation

### Layout and source of truth

Logical roles remain USER `flashydex-user.db`, `catalog-en.db`, `catalog-ja.db`. Actual sahpool names are absolute and private, for example `/flashydex-user.db`, `/catalog-en/g-<job>.db`, `/catalog-ja/g-<job>.db`. Catalog generation names do NOT change when activated; immutability means naming/lifecycle, not read-only contents: API refresh can write the current generation under its single connection. No personal rows in a catalog. An absent language opens no file. A fresh USER is created only after checking the migration marker and both legacy/new stores, never as an error fallback.

Pool paths are VIRTUAL names mapped to opaque OPFS files containing a VFS header. Never getFileHandle on the virtual DB path, write into opaque files, rename them, hand them to a decoder or depend on the private metadata/header offset. `getFileNames()` enumerates VFS contents; `unlink()` deletes a CLOSED generation only. `exportFile()` returns a whole Uint8Array and is prohibited for catalogs. Public PoolUtil has NO rename API. [S1, S3]

Ordinary OPFS staging lives OUTSIDE that directory: `/flashydex-staging/<job>/pack.zst.part` and `catalog.db.part`. Small adapter-only IndexedDB database `flashydex-web-storage-v1` holds role mappings, migration/import intent and activation metadata, NOT catalog bytes or personal rows. Version its schema, use one readwrite transaction for role changes, await transaction COMPLETE (strict durability hint where supported; do not pretend browser fsync is universally exposed), and validate on reopen. Store state per language: activeRef, previousRef, candidateRefs with job/version/hash/length; refs include kind+generation and are validated/confined. This metadata adapts existing `CatalogInstallPort`, it is not a new core schema or second collection authority. USER's existing installed_catalogs + install journal is the activation COMMIT authority; metadata supplies physical role state/recovery truth.

### Stream, verify, import — no whole buffers

1. Persist platform import intent and existing core job before allocation. Preflight origin estimate, pool slots, supported manifest/schema/origin. Stream fetch into the ordinary compressed staging file; count exact compressed bytes and validate optional compressed hash. Use default stream reader, not Safari BYOB requirements; no `response.arrayBuffer()`/Blob for the pack. Complete download/size check before decode, matching CATALOG-PACKS. Interrupted Phase 1 download/decode restarts; no new resume promise.
2. Dedicated decoder worker opens ordinary OPFS output with `createSyncAccessHandle`, truncates to zero, streams zstd output into checked writes at explicit offsets, retries short writes or fails, updates incremental SHA-256 and byte counts. Max32 MiB zstd window, output chunks<=256 KiB and <=4 unacknowledged chunks across the entire pipeline (<=1 MiB output relay); bound compressed pending inputs as well. The decoder may own both input and output handles directly on web; no main-thread file bridge required. Flush/close at EOF. Reject malformed/truncated frame, exact-size mismatch, overrun, hash mismatch, unsupported window, quota or cancellation; old active untouched. No concatenating output, one-shot decoder, `.text()` or whole-file WebCrypto digest.
3. Verify SQLite header and DELETE-mode header bytes 18/19 are both 1. Reserve the UNIQUE candidate path through public OO1 before async import: create a tiny throwaway DB at that path, write a bundled placeholder table, then close it; record only import intent, not a validated candidate. This deliberately associates its SAH with the path. The inspected `importDbChunked` selects a free SAH without removing it from the free set until the import finishes; importing a new unassociated path while USER work allocates a journal could otherwise reuse that SAH. Never allow that race. Pre-associated closed candidate + per-path exclusive import ownership lets unrelated USER SQL continue; if pinned behavior differs, hold a VFS-wide import admission barrier (no SQL/pool allocation interleaving) until verified, never trust await serialization implicitly. Do not await core progress writes from inside such a barrier.

   Then the SQL worker calls `await pool.importDb(uniqueCandidatePath, async chunkSupplier)`, not the full-array overload. Supplier reads the CLOSED ordinary staged file in <=256 KiB slices (or with its own worker sync handle), returns Uint8Array/ArrayBuffer, EOF `undefined`, and honors backpressure. This adds a streamed file-to-file COPY and transient disk cost, NOT a whole-memory import. Decoder never opens the sahpool's internal SAHs. Do not import into an OPEN or active DB; do not open the reserved candidate until import has completely settled. The placeholder is overwritten, never a valid product catalog. [S1, S3]
4. The public import only checks plausibility, not schema/integrity/authenticity; after success core opens the candidate through `openForValidation` and performs its bundled validation queries/counts/fingerprint/foreign_key_check/integrity checks, closes it, then rereads metadata as needed. The inspected import implementation writes in chunks and flushes through its path-association helper (`setAssociatedPath` in the pinned npm build; `setClientPath` in fetched upstream trunk); validate pinned behavior in browser fault tests. `importDb` forces SQLite header bytes18/19 to DELETE mode; checking they were already 1 prevents changing our verified pack digest. Hash the chunk supplier too and compare imported byte count; imports must preserve exact bytes for valid DELETE packs. Do not replace this with `exportFile` to rehash the import. Optional read-back audit must use bounded SQLite/VFS reads, not undocumented raw file offsets.
5. Mark candidate durable in adapter metadata only after successful import/close and checks. Retain ordinary stage until successful import validation, then remove it; compressed stage can now be removed too. Crash before metadata registration leaves a recognizable generation orphan, reconciled against import intent + core journal + pool enumeration at boot. Never sweep any unknown USER-like file or possibly referenced rollback source.

### Activation uses a small atomic pointer transaction, not fictional rename

The native installer keeps its journaled two-rename semantics. On web `CatalogInstallPort.activate(language,candidateRef)` implements equivalent LOGICAL atomic activation through role mappings; do not report filesystem `atomicRename:true`. Existing core already supplies PREPARED journal, catalog barrier, active validation, receipt commit and rollback calls. Keep that service unchanged. [R2]

1. Core durably writes PREPARED (old receipt + candidate ref) in USER before activate. Under existing language maintenance barrier stop/fence refresh, drain all affected wrapper queues, finalize/close that language's physical handle. USER and other language may remain open; do not pause the whole VFS.
2. In ONE adapter IndexedDB readwrite transaction, verify expected active/candidate generation, set previousRef=old active (or null), activeRef=candidate, remove candidate from candidateRefs. Physical files remain in place. Await transaction completion before returning `{activeRef,previousRef}`. If aborted, no roles change. Candidate membership is consumed at this transition to match core undoSwap/first-install recovery expectations. Never overwrite or unlink old active in activate.
3. Core reopens/validates new active; commits installed_catalogs.active_ref/version/hash/generation AND journal committed in one USER transaction. Only this durable core receipt commits product activation. Release barrier/invalidate caches after that acknowledgement. No atomic transaction spans IDB and OPFS SQLite; journal recovery bridges the interval. If COMMIT outcome is unknown, freeze writes/cleanup and recover from actual reopened state, never delete either generation based on memory.
4. `restorePrevious` atomically switches mapping back without renaming/copying bytes, closes target handles first, and keeps evidence until old state validates. `inspect` reads actual committed adapter mappings and verifies mapped paths exist in `getFileNames`, not cached JS fields. `discardPrevious` only removes a closed prior catalog after core durable success, never USER/current/candidate/recovery evidence. `discardCandidate(ref)` is membership-checked and idempotent: a promoted active/previous ref is NEVER unlinked, even if core error cleanup still holds its old candidateRef after an uncertain receipt COMMIT. Garbage collection is journal-aware and idempotent. `capabilities.atomicActivation` may become true only after all pointer+core-journal fault tests pass; attachReads=false, catalogWrites=true, fullInstall=true only after worker/streaming/capability gates pass. Current unconditional fullInstall/limited-mode copy is not release evidence.

| Crash/fault point | Required recovery before exposing catalogs |
|---|---|
| transfer/decode/chunked import incomplete | Old active remains; reconcile intent, remove only proven unreferenced parts; mark interrupted, Retry. |
| PREPARED, pointer transaction not committed | Existing active/membership unchanged; discard staged candidate only after journal reconciliation. |
| Pointer committed, no committed new USER receipt | Previous remains; core inspect/undoSwap restores previous. First install returns to no catalog, not empty DB. |
| USER receipt COMMIT uncertain | Reopen USER; actual durable receipt/journal determines direction. Do not roll back a committed install or erase rollback evidence on a guess. |
| Receipt committed, cleanup interrupted | Validate active, finish bounded cleanup. |
| New active fails validation, previous valid | Restore previous and old receipt; owned/custom/settings/history byte-for-byte unchanged. Neither valid ->isolate catalog and offer redownload; USER still opens. |

Disk preflight must account for the extra sahpool import copy: additional free space >= compressedBytes + 2*uncompressedBytes + journal/metadata overhead + max(32 MiB, 10% of uncompressedBytes). Existing estimate.usage ALREADY includes active/previous USER/catalog/cache data; do not double-count it as free. Peak footprint report separately lists old active, compressed stage, ordinary raw stage, new pool candidate, pool headers/sidecars, USER and image cache. Sixteen pool slots do not reserve these bytes. Evict only replaceable images/abandoned proven parts first; mid-install quota failure keeps working catalog and personal data. [S7, S8]

## 5. One-time migration from jeep IndexedDB

Legacy evidence: `jeepSqliteStore` / object store `databases`, key `flashydex-userSQLite.db`; catalog keys are replaceable and MUST NOT be loaded/exported for migration. The old flush path reads a prior full array and jeep removes a key before writing; keep legacy bytes as a safety source, do not call its save/close autosave to "migrate" data. [R1]

Under `flashydex-user-writer` lock and before normal createUserDriver:

1. Inspect a versioned migration marker and existence/validity of new USER/legacy USER. Never treat a corrupt/unreadable new USER as an empty first run. If new USER with committed migration marker validates, use it and do not replay stale legacy data. If both contain differing personal data without a completion marker, block automatic merge and offer recover/export selection.
2. Read ONLY the legacy user DB bytes from IndexedDB (the legacy raw SQLite export). Prefer this persisted export to constructing jeep; first verify type, SQLite header, supported schema fingerprint/version and bounded user size. If an old release used another encoding, pin/test an explicit migration-only exporter; do not guess its internals. Catalogs re-download; migrate all USER personal entities/settings/customs/history, not only owned_cards. Clear/reset installed_catalogs/sync/install operational refs through existing platform startup/recovery paths so stale jeep catalog receipts are not treated as OPFS files; preserve selected/followed language preferences without automatic download.
3. Import into a UNIQUE staged USER path with chunked `pool.importDb`, validate integrity/FKs, bundled USER migration compatibility, canonical counts/UUIDs/values for all personal tables. A legacy IDB value is already one complete user byte array: this one-time USER-only exception is explicitly measured/capped, not permission for a catalog copy. Provisional automatic migration cap16 MiB; larger legacy user data goes through bounded row/JSON export/import recovery, not silent deletion or a full-catalog buffer. Do not instantiate sql.js and OPFS copies together unnecessarily; release legacy arrays after successful validation.
4. Run existing trusted migrations/recovery with staged USER through platform injection. Operational catalog receipts require care: only use existing core services/migrations or platform-executed bundled operational reset SQL (no schema changes); mark catalogs absent, release abandoned work, and never alter personal rows/revision as a migration shortcut. If this cannot be expressed safely with current interfaces, report the precise interface blocker before touching core.
5. Commit small adapter migration marker + active USER role mapping in one IDB transaction after staged OPFS DB closes/flushes and validation succeeds. Reload/reopen through the new driver; read back exact personal contents and settings. Crash before marker leaves original legacy export authoritative; crash after marker uses new staged/activated USER and validates it, never replays the old export. Retain legacy USER key until the user has a verified external backup and an explicit cleanup action. Do not delete unrelated IndexedDB data. Old catalog keys may be cleared only with explicit replacement/cleanup policy after migration, never deserialized just to delete.

### Byte-bounded image LRU (web Phase 1, native seam unchanged)

Promote the SW cache implementation for `https://assets.tcgdex.net` into web Phase1, rather than deferring the cap to Phase7. Only images actually viewed, low.webp for grids and high.webp for explicit detail/zoom. Default limit200,000,000 payload bytes, configurable150,000,000..250,000,000. Cache API cannot limit bytes natively; Workbox maxEntries is NOT a byte cap. [S12]

Implementation contract:

1. SW image handler requests allowlisted HTTPS URL with `mode:'cors', credentials:'omit'`. Cache only status200 readable image/webp responses. Opaque/no-CORS bodies cannot be measured; pass through without caching, never count them as zero. Missing art/fetch/quota error is a styled placeholder or uncached network response, not catalog/user-data failure.
2. Maintain separate image-only Cache Storage name plus IndexedDB metadata `{url,bytes,lastAccess,storedAt,state}`, ledger totals and reservations. Bound each admitted response to2,000,000 bytes by counted stream reads (do not trust Content-Length); over-limit/opaque response bypasses cache. A small per-image buffer/Blob is allowed within this cap; NEVER buffer a pack. Keep at most one cache admission buffer active, bound any network response tees too, and stop body reads at the cap. Browser disk overhead isn't equal to payload length: label the enforced cap as stored-response payload bytes, reserve quota headroom and report actual origin estimate separately.
3. Serialize admissions/evictions/reconciliation across SW events with a dedicated Web Lock `flashydex-image-cache` plus SW-local queue. Cache hits update lastAccess in a bounded write/debounce path held by event.waitUntil; worker termination may lose a recent touch, never invalidate totals. Use cache-first for offline hits, freshness TTL30 days with one bounded background revalidation on later online use (conditional when server supports it), no bulk prefetch.
4. Before cache.put, evict oldest committed entries until committedBytes + reservedBytes + newBytes <= limit (replacement subtracts old charge only after old entry is actually deleted). Record a durable pending reservation first, then write cache entry, then mark committed and charge actual bytes in metadata transaction. A SW-local Promise alone is not restart safety; Cache Storage and IDB cannot commit atomically. On SW start/activation and after any storage error reconcile cache.keys against ledger: remove pending/untracked entries rather than retaining uncharged bytes, remove missing metadata entries, recompute totals; evict to cap BEFORE admitting another entry. Expire abandoned reservations and reconcile under the same lock, never race active put. Crash after put but before metadata commit leaves a charged reservation or an orphan that reconciliation deletes. Enforce committed+pending budget throughout, not eventually after overshooting.
5. On QuotaExceededError stop image admissions, reconcile/evict and retry at most once; leave app usable even if caching is disabled. Settings limit reduction/clear sends versioned SW message+ACK, takes same lock and evicts immediately. Platform.imageCache maps to SW stats/clear/setLimit without core changes; report enforced=true only when actual SW byte ledger/recovery is active. Otherwise honest unavailable/enforced=false plus release gate outstanding. Never clear USER/OPFS/catalogs/custom images to recover the image cache.

Cache Storage and OPFS share the origin eviction risk; a200 MB art cap does not reserve USER durability. Explain offline art is best-effort and cleared images never remove owned cards.
